# QR Payload Reference

This document describes every QR payload type generated by the Stellar Disaster
Relief Payments SDK, what each field reveals, the expiry/scoping mechanism, and
guidance for scanning parties.

---

## Design Principles

1. **Minimum necessary data.** QR codes must contain only the fields a scanner
   needs to complete a single, well-scoped action. Balances, names, and other
   sensitive state should be fetched from the contract after scanning, not
   embedded in the QR.
2. **QR-specific expiry.** Every QR carries a `qrExpiresAt` timestamp that is
   independent of the on-chain resource's own expiry. This prevents screenshots
   and printed QR images from being replayed indefinitely.
3. **Version field.** Every payload includes `v: 1` so parsers can handle future
   schema changes without breaking backward compatibility.
4. **No raw PII.** Beneficiary real names, national IDs, biometric data, and
   contact information must never appear in any QR payload.

---

## Payload Types

### 1. Beneficiary ID QR

**Generator:** `BeneficiaryClient.generateBeneficiaryQRCode()`
**Default QR TTL:** 30 minutes
**Used for:** Field agent verification, merchant payment initiation

```json
{
  "type": "beneficiary_id",
  "v": 1,
  "beneficiaryId": "<opaque-id>",
  "disasterId": "<disaster-programme-id>",
  "trustScore": 75,
  "qrExpiresAt": 1700000000000,
  "timestamp": 1699998200000
}
```

| Field | Reveals to scanner | Notes |
|---|---|---|
| `beneficiaryId` | Opaque programme token | Not a real name; not reversible |
| `disasterId` | Programme identifier | Non-identifying |
| `trustScore` | Aggregate 0-100 score | No raw behavioural data |
| `qrExpiresAt` | Expiry timestamp | Prevents stale QR replay |

**Omitted fields (vs previous implementation):**
- `name` - removed to prevent name exposure via QR photography
- `verificationFactors` - not needed for presentation scanning; fetched on-chain

**Scanner guidance:**
After validating `qrExpiresAt`, call `getBeneficiary(beneficiaryId)` to obtain
the full profile (including name and verification status) through authenticated
access before completing the transaction.

### 2. Fund QR

**Generator:** `AidClient.generateFundQRCode()`
**Default QR TTL:** 24 hours
**Used for:** Field agent fund lookup, offline fund verification

```json
{
  "type": "emergency_fund",
  "v": 1,
  "fundId": "<opaque-fund-id>",
  "disasterType": "earthquake",
  "name": "Earthquake Response Fund",
  "fundExpiresAt": 1710000000000,
  "qrExpiresAt": 1700086400000,
  "timestamp": 1700000000000
}
```

| Field | Reveals to scanner | Notes |
|---|---|---|
| `fundId` | Opaque fund identifier | |
| `disasterType` | Programme category | Non-identifying |
| `name` | Fund display name | No PII; human-readable label |
| `fundExpiresAt` | When the fund expires on-chain | Not a security boundary for the QR |
| `qrExpiresAt` | When this QR image expires | Security boundary for replay prevention |

**Omitted fields (vs previous implementation):**
- `totalAmount` - removed to prevent financial detail exposure via QR photography;
  amounts are on-chain and must be queried via `getFund(fundId)` after scanning

**Scanner guidance:**
Check `qrExpiresAt` before `fundExpiresAt`. Call `getFund(fundId)` to obtain
live financial state (total amount, released amount, status) after validating
the QR.

---

### 3. Transfer QR

**Generator:** `TransferClient.generateTransferQRCode()`
**Default QR TTL:** 30 minutes
**Used for:** Merchant payment acceptance at point of sale

```json
{
  "type": "transfer",
  "v": 1,
  "transferId": "<opaque-transfer-id>",
  "beneficiaryId": "<opaque-beneficiary-id>",
  "amount": "1000",
  "token": "XLM",
  "purpose": "emergency_earthquake_relief",
  "spendingRules": [
    { "type": "category_limit", "limit": "400" }
  ],
  "transferExpiresAt": 1702592000000,
  "qrExpiresAt": 1700001800000,
  "timestamp": 1700000000000
}
```

| Field | Reveals to scanner | Notes |
|---|---|---|
| `transferId` | Opaque transfer identifier | |
| `beneficiaryId` | Opaque beneficiary token | Not a name; links to on-chain record |
| `amount` | Original allocated amount | Needed for offline pre-check only |
| `token` | Asset type (e.g. XLM) | |
| `purpose` | Transfer programme code | Use category codes, not free-text descriptions |
| `spendingRules` | Category limits | Rule types and limits only |
| `transferExpiresAt` | When the transfer expires on-chain | |
| `qrExpiresAt` | When this QR image expires | 30-min default |

**Omitted fields (vs previous implementation):**
- `remainingAmount` - removed to prevent live balance exposure via QR photography.
  A photographed or screenshotted transfer QR would previously reveal the
  beneficiary's exact remaining balance to anyone who scanned it.

**Scanner guidance:**
Check `qrExpiresAt` before processing. Call `getTransfer(transferId)` to obtain
the current `remainingAmount` before completing the payment. Never trust the
`amount` embedded in the QR for the final payment amount - always query the
contract for live state.

### 4. Offline Auth QR (reference implementation)

**Generator:** `OfflineAuthClient.generateQRCode()`
**Default QR TTL:** 30 minutes (configurable via `validityMinutes`)
**Used for:** Offline beneficiary verification without internet connectivity

```json
{
  "v": 1,
  "id": "<idHash-first-16-chars>",
  "ts": 1700000000000,
  "exp": 1700001800000,
  "trust": 75,
  "loc": "Camp Alpha, Zone 3",
  "sig": "<sha256-truncated-32-chars>"
}
```

| Field | Reveals to scanner | Notes |
|---|---|---|
| `id` | First 16 chars of SHA-256 idHash | Pseudonymous; not reversible to name |
| `ts` | QR generation timestamp | |
| `exp` | QR expiry timestamp | Hard expiry enforced by validator |
| `trust` | Trust score (0-100) | |
| `loc` | Camp location string | Camp-level granularity only |
| `sig` | Truncated SHA-256 signature | Time-based; covers id + ts + exp + trust |

This is the **most secure and private** QR type in the SDK:
- Uses a cryptographic time-based signature.
- `id` is the shortened idHash (pseudonymous, not the beneficiary ID or name).
- All field names are abbreviated to minimise QR image size.
- Expiry is mandatory and enforced by `validateQRCode()`.

Use this generator for any context that requires fully offline cryptographic
verification.

---

### 5. Merchant Static QR

**Generator:** `MerchantNetworkSDK.generateQRCode()` (calls `generate_shop_qr` on-chain)
**Default QR TTL:** None (static; rotated by re-generating)
**Used for:** Directing beneficiaries to a merchant's point of sale

Pipe-delimited string format: `merchantId|category|latitude|longitude|name`

| Field | Reveals to scanner | Notes |
|---|---|---|
| `merchantId` | Opaque merchant identifier | |
| `category` | Merchant category code (integer) | |
| `latitude` | Geographic latitude | Consider rounding to 2 d.p. (~1 km) for public QR |
| `longitude` | Geographic longitude | Same as latitude |
| `name` | Merchant display name | Intentionally public |

Merchant data is intentionally public for network discovery. However, operators
should consider rounding `latitude` and `longitude` to 2 decimal places (~1 km
precision) for the QR payload to avoid exposing the precise interior location of
a shop.

**No expiry mechanism.** Rotate by calling `generateQRCode()` again when the
merchant's location or category changes.

---

### 6. Transaction QR

**Generator:** `MerchantNetworkSDK.generateTransactionQR()` (calls `generate_transaction_qr` on-chain)
**Default QR TTL:** Immediate use only (no TTL field in payload)
**Used for:** Single-use payment initiation at merchant POS

| Field | Reveals to scanner | Notes |
|---|---|---|
| `merchantId` | Opaque merchant identifier | |
| `amount` | Payment amount | Visible to anyone scanning |
| `transferCode` | Payment code | Short-lived by intent |
| `timestamp` | Generation timestamp | |

This QR is generated per-transaction and must be used immediately. The
`timestamp` should be validated by the scanning party to reject stale QR codes
(recommended: reject if `Date.now() - timestamp > 5 * 60 * 1000`).

---

## Validation Checklist for Scanner Implementations

All QR scanner implementations must:

1. Parse and validate the `type` field before any further processing.
2. Check `qrExpiresAt` (or `exp` in Offline Auth QR) before making any
   network calls. Reject expired QRs immediately.
3. Never use amounts embedded in the QR as the source of truth for payment.
   Always query the contract for live state after scanning.
4. Log all QR scan events for audit purposes (scanner identity, timestamp,
   beneficiary/transfer/merchant ID).
5. Never display the full raw QR payload to end users - show only the
   human-readable fields (name, trust score, amount category) after
   on-chain verification.

## Expiry Quick Reference

| QR Type | Default TTL | Configurable |
|---|---|---|
| Beneficiary ID QR | 30 minutes | Yes (`qrTtlMs` parameter) |
| Fund QR | 24 hours | Yes (`qrTtlMs` parameter) |
| Transfer QR | 30 minutes | Yes (`qrTtlMs` parameter) |
| Offline Auth QR | 30 minutes | Yes (`validityMinutes` parameter) |
| Merchant Static QR | No expiry | Manual rotation |
| Transaction QR | Immediate use | No - reject if `timestamp` > 5 min old |
